# hermesd 2026.9.13

hermesd 2026.9.13 brings deeper visibility into your Hermes Agent: gateway
responsiveness, session coordination, scheduled work, delegation progress,
plugin health, and recovery evidence. It also improves the accuracy of the
warnings and counts you use to decide whether something needs attention.

These notes cover **all changes since the last published release, v2026.7.11**,
including the unpublished 2026.9.8 development milestone and the subsequent
feature, reliability, security, and CI/CD reviews. Related corrections are
grouped below; descriptions reflect the final implementation rather than
intermediate versions that were replaced during review.

hermesd remains independently installed and read-only: it does not import
Hermes Agent code or change your agent's files. Missing evidence is labelled
as missing or unverifiable instead of being treated as proof of health.

## Gateway health and shared listeners

- **Loop responsiveness:** the gateway's loop-tick witness provides a direct
  response signal, alongside heartbeat age. A fresh heartbeat alone no longer
  proves the event loop is dispatching work. Legacy and unverifiable writers
  remain distinguishable.
- **Reliable stalled-loop warnings:** escalation uses the 90-second stale
  budget and consecutive silent probes. Silence counters reset for a different
  witness PID, avoiding false alarms after a gateway restart.
- **Crash and restart evidence:** lifecycle phase, last exit code/reason,
  previous unclean exit, suspected OOM, restart counts, incarnation uptime,
  and the exit-diagnostic ledger are visible. Companion diagnostic logs show
  file metadata without loading their contents.
- **Configured restart policy:** respawn-storm counts use your configured
  window and limit, including a disabled policy. Unparseable start records
  are not reported as zero starts; future exit timestamps are excluded from
  the recent-exit count. An unclean exit can also follow a forced replacement,
  which the panel now explains.
  Non-finite, non-positive, or overflowing windows fall back safely instead
  of crashing a detail panel or text snapshot.
- **Writer ownership:** platform rows distinguish current, preserved, and
  unverifiable records using writer identity. An unrelated or recycled PID
  cannot make an old gateway record authoritative.
- **Shared-listener routing:** profile-qualified platforms, served-profile
  evidence, recorded ingress URLs, and per-profile listener mirrors are
  shown. Bare paths, unknown topology, and truncated rosters are labelled.
  URLs are redacted and shown only under the appropriate writer and adapter
  state rules; hermesd does not request those URLs.
- **Web-dashboard presence:** a recent dashboard-client heartbeat adds an
  attachment indicator without claiming a full client inventory.
- **Running build and configuration:** code SHA/version, session-store status,
  config evidence, platform attention/retry metadata, drain timing, and
  migration evidence are visible. Config staleness uses the running gateway's
  start time rather than obsolete config-generation timestamps; unknown start
  time is not presented as a definite stale-config verdict.
- **Migration verification:** migration intent is distinguished from verified
  shared-listener state. Unsupported manifest schemas or malformed default/
  secondary profile records remain visible without producing a verified verdict.
- **Update receipts:** version transitions, outcomes, failed steps, and fleet
  state are shown. Code-skew checks prefer post-restart fleet evidence;
  incomplete updates can fall back to their plan. Successful receipts no longer
  appear failed, and unavailable evidence is not presented as a clean fleet.
- **Delivery obligations:** pending/failed deliveries and recent undelivered
  records expose delivery trouble without reading message bodies.
- Gateway detail now separates liveness facts onto readable lines, redacts
  diagnostic tags, and labels the latest diagnostic as a record rather than
  assuming it is an exit.

## Sessions, coordination, and usage

- **Richer sessions:** display names, pinning, Git branch, profile, chat type,
  recent activity, billing source, and compression errors are surfaced when
  available. Hidden sessions are excluded from the normal list; recent ordering
  follows activity, including resumed sessions.
- **Verified active surfaces:** registry entries distinguish verified live,
  dead, and unverifiable owners using PID and process start time. Counts no
  longer equate recorded entries with executing sessions. Process probing is
  bounded, and oversized PIDs cannot fail the whole source.
- **Capacity and leases:** the active-session lease cap is shown separately
  from the in-memory session cap. Registry occupancy, distinct PIDs, verified
  activity, acquisition/update ages, and transferred leases remain separate
  facts. Display filtering and row limits do not change the reported totals.
- **Turn leases and compression locks:** holder, duration, expiry, and owner
  evidence help explain coordination delays. Expired leases may be revived by
  their holder; orphaned leases are distinguished, and compression locks are
  not described as blocking ordinary turns.
- **Compression recovery:** durable compressor recovery information and
  per-chat hygiene failure streaks expose recovery/cooldown state. Totals and
  rows survive a failed read together, and effect labels follow the computed
  state instead of duplicating a threshold in the renderer.
- **Routing recovery:** suspended, resume-pending, auto-reset, dangling-target,
  and unfinished-turn evidence appears with bounded, redacted reasons. Hidden
  but resumable sessions no longer produce false dangling-route warnings.
- **Reset churn:** per-chat generations and lifetime reset totals expose
  reset activity. A shrinking generation table raises a persistent warning,
  including when it becomes empty, until its previous high-water count recovers.
- **Joinable sessions and CLI breadcrumbs:** joinable metadata appears as a
  chip without probing or exposing the attach URL. Recent terminal breadcrumbs
  show recorded session/cwd/age information without claiming the terminal is
  still alive; capped scans explicitly report incomplete counts.
- **Per-model usage:** the Tokens / Cost panel reads model-usage records for
  all-time, 24-hour, and 7-day breakdowns, including API calls, tokens, billed
  costs, estimates, and auxiliary task subtotals. Older schemas retain their
  per-session fallback.
- **Correct cost accounting:** cache-write tokens contribute to estimates;
  explicit billed zero remains zero. Mixed billed/estimated groups show both
  components, including auxiliary usage, without dropping estimates or
  double-counting billed rows.
- **Fresh analytics and search:** context-limit edits refresh dependent
  calculations, rolling windows age out during the day, and unchanged search
  queries refresh when data changes. New searches are not lost while the
  previous worker finishes. Compacted messages are excluded from active
  transcript searches and tool statistics; fallback search results are bounded.

## Cron scheduling and incident visibility

- **Execution history:** per-job recorded attempts, latest result, duration,
  error excerpt, recent executions, and 24-hour totals are available from the
  executions store. Unknown results have an explicit bucket and denominator.
- **Execution versus delivery:** delivery outcomes, scheduled instants,
  pending handoffs, and per-job delivery summaries are reported independently
  of whether the job completed. Older schemas do not imply delivery tracking.
- **Retention-aware totals:** the panel exposes the retained history span and
  cap. Aggregates use the full retained time window rather than a display-row
  sample, and per-job last results are not crowded out by busy jobs.
- **Dispatch integrity:** fire claims, owner liveness, pending slots, fire
  errors, preflight evidence, and dispatch snapshots make stalled handoffs
  easier to inspect. Same-host claims whose owner is provably gone no longer
  remain labelled running until TTL expiry; foreign owners stay unverifiable.
- **Ticker and catch-up state:** heartbeat/last-success ages, ticker errors,
  catch-up policy and counters, dispatch lateness/kind, repeat progress,
  failure streaks, pauses, no-agent jobs, and delivery errors are surfaced.
- **Incident semantics:** open and unacknowledged incidents remain separate.
  Open incidents cannot be acknowledged independently of the closing transition.
  Detecting an incident is not proof that the alert-delivery path failed.
  Fire errors include useful age context.
- **Actionable status wording:** queued deliveries remain unverified with a
  do-not-resend warning; preflight blocks point to configuration rather than a
  rerun. Unpinned jobs expose their recorded model/provider snapshots.
- Null and wrong-typed job fields no longer fail the whole source. Enabled,
  no-agent, preflight, and execution-handoff flags use strict machine-payload
  parsing. A pause timestamp is sufficient to show a paused job even without
  a reason string.
- Timestamps normalize offset-aware and naive-as-UTC execution records, handle
  unusual stored epoch types, and break ties deterministically. Job detail can
  retain a useful execution error after jobs.json has cleared its copy.
- Execution, incident, ticker, and output failures preserve their own last-good
  evidence. Output caching follows the file actually read, retries unusable
  timestamps, and bounds lines before redaction.

## Kanban boards and notifications

- **Notification backlog:** subscriber counts, per-platform totals, unseen
  events, worst backlog, delivery mode, owning profile, cursors, and orphaned
  profile routes are visible alongside the task board.
- Backlog counts include only the subscription's own events newer than its
  cursor. Unrelated task events cannot inflate the total. The displayed worst
  backlogs are bounded while aggregate counts remain complete; the default
  profile is not falsely considered orphaned.
- **Completion contracts:** task metadata shows local, repository, or PR
  completion requirements, helping explain cards waiting in review. Contract
  text is redacted at collection time.
- **Failure breakers:** configured/per-task limits and consecutive failure
  counts explain blocked redispatch. Explicit zero is preserved separately
  from an absent limit, but a healthy task with no failures does not display a
  tripped breaker. Compact view identifies affected tasks.
- A corrupt individual board no longer discards healthy boards. Query and WAL
  copy failures preserve last-good summaries and report degraded health.
  A WAL-mode database with no sidecars can use the immutable read path;
  an unreadable existing WAL sidecar is not silently ignored.
- Board readers share one WAL copy per refresh. Completion times render as
  ages, and literal brackets in compact text no longer acquire stray escapes.

## Operations, delegations, and recovery

- **Async delegations:** state, delivery attempts, owner evidence, duration,
  goal, result/error excerpts, and running/failed/undelivered counts are shown.
- **Delegation manifests:** recent cards show model/provider, task status,
  exit reason, and redacted task-log tails. Task totals derive from manifest
  entries, unreadable counted manifests are identified, and only displayed
  task logs are opened. Directory age means dispatched time; manifest count
  does not mean every run is live.
  Malformed counts cover the full bounded candidate scan even after the five
  displayed cards are filled, without reading additional task logs.
- **Process handoffs and receipts:** delegation results expose handed-off,
  orphaned, and unread-completion counts. Profile-scoped completion receipts
  show exit reason/code and redacted output tails; missing receipts remain a
  valid quiet state under retention. Redaction happens before tail clipping.
- **PR monitoring:** current keyed PR-monitor records are recognized, with
  tracked/open/conflicting counts and last-checked time. Backup/lock siblings
  are ignored.
- **State DB evidence:** schema version, DB/WAL size, file generation, FTS
  version, and prune/archive metadata share the cached state read. Missing
  optional tables remain supported; read errors cannot masquerade as zeros.
- **Database recovery:** failed-repair ledger, recorded budget exhaustion,
  settled malformed backups, retired WAL generations, in-progress captures,
  and lock-file presence are visible. This reader does not repair, hash, or
  integrity-check the database. A lock file is not proof of a held lock, and
  absent failure records are not proof the database is healthy.
- **Hosted rooms:** the root shared-state store supplies room/member counts,
  event-kind totals, links, remote runs, retired IDs, revoked grants, and
  live/expired/revoked peer reservations. Room lists are bounded independently
  of totals. Conversation bodies, grants, actor identities, and link secrets
  are excluded from collection.
- **Retained API run reservations:** the profile-scoped idempotency store
  supplies status, timing, retention, acknowledgement, and ownership evidence.
  This is a replay window, not a complete activity ledger; an empty store does
  not prove an idle API, and hermesd does not claim to detect an in-memory
  fallback from on-disk evidence.
- **Additional evidence:** state-snapshot counts/size/age, web/desktop build
  stamps, blocked-script presence, corrupt spawn-ledger markers, and checkpoint
  prune timing are shown. Prune warnings honor the configured cadence and do
  not equate a fresh marker with successful pruning.
  Non-finite or overflowed prune intervals retain the default cadence and
  remain safe to render.
- Ages use the collection clock, file timestamps handle platform edge cases,
  and an unreadable source does not erase unrelated Operations sections.

## Tools, configuration, skills, and Curator

- **Current tool/process inventory:** available tools and toolset availability
  come from the current banner snapshot, with a bounded legacy session-file
  fallback. Spawn-ledger processes show purpose, port, profile, and PID evidence;
  the old process file remains a fallback. Checkpoint summaries tolerate
  non-UTF-8 subjects and refresh when repository refs change.
- **Current configuration keys:** delegation, goals, updates, plugins, MCP,
  loop guardrails, streaming, logging, network, and session limits follow the
  supported Agent shapes. Counts, names, and presence flags avoid exposing
  credential values. Incorrect legacy key lookups and type coercion are fixed.
- **Config backup evidence:** good/corrupt/pre-setup/migration snapshots show
  changes and recovery history. Corrupt copies are prominent; grouping caps
  cannot hide the newest good copy or corrupt-copy warning. Snapshot age is
  not mislabelled as a stale reader when config has not changed.
- **Plugin inventory and provenance:** supported manifest formats, install
  provenance, and activation states distinguish removed, disabled, category-
  owned, not-enabled, and unknown plugins. Being installed does not prove a
  plugin loaded. Provider detection reads bounded source text without executing it.
  Portable manifests follow the upstream field-validation rules; inferred
  provider kinds apply only when the kind field is absent.
- **Catalog drift:** available updates, removals, and unmanaged installations
  are compared with the cached catalog. An absent, corrupt, or unreadable cache
  means checks are unavailable, not that installed plugins are current.
- **Desktop plugins:** a separate, bounded inventory reports plugin.js presence
  without reading JavaScript or claiming activation.
- **MCP and skills snapshots:** configured/cache membership, cache validity and
  age, and prompted-skills snapshots
  are surfaced. Membership uses complete sets before display truncation;
  missing cache entries are not described as never-connected servers.
  Entry validity uses its own write time and recorded TTL, distinguishing
  valid, expired, and unassessable entries rather than relying on file age.
- **Nous free tier:** the provider badge follows the recorded anonymous
  authentication method rather than inferring eligibility from other fields.
- **Curator hygiene:** patch reuse, active/stale/archived/unknown state counts,
  pinned skills, and stale/archive threshold windows use the configured policy.
  The rollup remains present when run reports exist, and malformed/infinite
  thresholds cannot blank the entire source.
- Memory inventories exclude lock files and hidden bookkeeping entries.

## Terminal usability, snapshots, and profiles

- Sessions and Config detail views scroll as whole views so lower sections
  and alerts remain reachable on ordinary terminals. Navigation hints follow
  actual scroll support; offsets clamp after filtering, resizing, and at zero.
- Clipboard export copies the current rendered view as plain text, performs
  expensive rendering outside the view lock, and caps OSC 52 output with a
  truncation marker. Snapshot/copy rendering uses a consistent view snapshot.
- Snapshot files create missing parents and are replaced atomically. A hard
  link to protected agent state cannot be used to truncate that state; partial
  temporary output is cleaned up after failures.
- Snapshot interruption uses conventional SIGINT/SIGTERM exit codes and useful
  messages; a second signal can stop a stuck collection. Render failures
  restore the terminal before reporting a concise error.
- Input survives bounded transient terminal errors and split escape sequences.
  The render loop avoids busy waiting, view mutations share the appropriate
  lock, shutdown interrupts message search before closing SQLite, and quitting
  can stop collection after the current source.
- Log streams state their root/profile ownership in detail and JSON snapshots.
  Profile readers revalidate confinement, including sibling-profile boundaries,
  on each read. Root-only default and explicit profile selection remain intact.
- Logs can fall back to a nonempty stream, long tables state their display caps,
  Skills navigation remains bounded, and Unicode/CJK and negative token values
  render correctly.

## Read-only safety, privacy, and resilience

- Live WAL databases use private temporary copies where required to preserve
  zero writes, including same-process writers. State consumers reuse a cached
  copy; missing versus unreadable WAL sidecars are distinguished.
- Per-source last-good data continues advancing while another source fails.
  SQLite query/schema errors, stale YAML, corrupt caches, and unreadable
  directories report degraded health instead of false empty results. Genuine
  deletion evicts cached files; temporary I/O failures retry without requiring
  another edit. Last-good theme/config remain usable through malformed writes.
- Nanosecond file signatures detect rapid changes; tool cache signatures track
  individual paths, and context/window cache keys include their dependencies.
  JSON/YAML reads enforce an 8 MiB ceiling during reading, plain-text reads
  have bounded limits, log tail byte limits survive concurrent growth, and
  capped directory scans apply their cap before materializing the whole list.
- Machine-written booleans are read strictly across gateway, sessions, routing,
  cron, channels, updates, drains, processes, curator, migration, and skill
  usage records. Stringified false and non-finite numbers cannot enable flags.
  Human-authored settings retain their deliberately compatible semantics.
- Deeply nested or malformed JSON is handled safely in readers and redaction.
  Nulls, unusual SQLite numeric types, invalid UTF-8, oversized PIDs, and
  implausible timestamps no longer take down unrelated dashboard sections.
- Secret redaction covers structured/nested values, quoted and multi-word
  secrets, truncated text, URL userinfo and secret query keys, uppercase or
  non-HTTP schemes, key=value URL arguments, billing labels, routing free text,
  delegation goals/receipts, completion contracts, and diagnostics.
  Sanitizing malformed URLs cannot itself crash collection.
- Every panel strips terminal-control sequences, including ANSI and
  OSC/DCS/APC payloads, from collected data. Rich markup-sensitive values are
  escaped appropriately. Log and redaction patterns are bounded to avoid
  pathological backtracking and oversized-line stalls.
- Paths and sidecars remain confined to their intended Hermes home, including
  symlinked parent directories and replacements after a successful read.
  Snapshot export and live readers retain independent read-only safeguards.

## Packaging, CI/CD, and contributor tooling

- Direct published runtime pins are **Rich 14.3.3, PyYAML 6.0.3, and Pydantic
  2.13.4**. The lock uses pydantic-core 2.46.4. Direct pins are checked against
  built-wheel metadata; this does not freeze every transitive dependency in
  a fresh package installation.
- Python 3.11–3.14 validation, branch coverage with a 96% gate, macOS testing,
  PTY/read-only/Unicode tests, and deterministic portability tests strengthen
  the compatibility checks. Runtime code remains compatible with Python 3.11.
- Static analysis and per-interpreter security have separate signals.
  Dependency review participates in the required aggregate CI gate. Change
  classification includes source, tests, helpers, docs, and release inputs;
  missing, failed, cancelled, or unexpectedly skipped required work fails closed.
- Weekly installed-environment and exported-lock audits detect new advisories
  without a code change. Scanner failures are classified separately, retried
  once, and remain blocking; malformed, inconsistent, incomplete, or skipped
  third-party evidence cannot appear clean.
- Release admission checks protected-main history and the newest attempt of
  the exact commit's main-push CI workflow. Release tests and fresh security
  checks remain; release test/build caching is disabled. Publication-environment
  and tag protection are separately managed: only `v*` tag deployments are
  allowed, administrator environment bypass is disabled, tag creation is
  restricted to repository administrators, and tag updates/deletion are blocked.
- Nix output structure is corrected and version metadata derives from the
  package manifest. Package realization runs pytest, installed CLI checks, and
  Git checkpoint smoke checks, with all four Linux/macOS architecture targets
  configured in CI. Nix uses its pinned package set, with the necessary
  Hatchling build dependency and Git available after installation.
  Intel macOS selects a separate immutable pin from the supported Nixpkgs
  26.05 Darwin branch; other systems retain the primary package set. Scanner
  fixtures run with their own interpreter in pure Nix sandboxes, and Nix jobs
  retain full build/test logs.
- Docker retains a pinned base, non-root execution, locked installation, and
  public CLI checkpoint smoke testing. Package permissions permit the runtime
  user to read its installation. Container distribution remains local-build-only.
- Wheels include typing metadata. Source distributions include the helpers,
  lockfile, workflows, and policy files needed by their tests. Wheel/sdist
  smoke tests run outside the checkout against synthetic populated, empty,
  and missing homes, checking text/JSON behavior and unchanged fixture contents.
- Packaging uses an SPDX MIT license expression and current core metadata.
  Pytest 9.1.1, Ruff 0.16.6, types-PyYAML 6.0.12.20260906, pip 26.2.1, and
  development-only cryptography 50.0.1 are in the validated lock.
- JUnit/coverage diagnostics are retained on success and failure. Dependabot
  groups routine action minor/patch updates while keeping major upgrades
  separate and retaining weekly source/container updates and security alerts.
- The collector is organized into per-domain modules behind its existing
  public facade, with shared parsing, WAL, formatting, and Curator helpers.
  Injected clocks/process evidence and deterministic failure tests reduce
  dependence on the host environment; coverage exclusions no longer hide
  real function bodies containing ellipses.
- Contributor guidance, source-ownership contracts, security reporting,
  troubleshooting, and dependency/release policy are consolidated and tested.
  Manual terminal, SSH/tmux, screenshot, and real-home acceptance checks remain
  part of release readiness.

## Compatibility and upgrade notes

- Requires Python **3.11 or later** for package installation; macOS and Linux
  remain the supported operating systems.
- No Hermes Agent migration is performed. Newer optional files/tables add
  evidence when present; older schemas retain supported fallbacks.
- JSON consumers should account for new evidence/count fields, stricter
  ownership/liveness states, and `gateway_starts_window` replacing the former
  fixed-window field `gateway_starts_2m`.
- A standalone macOS ARM64 executable is available for local manual testing;
  it does not establish a new maintained cross-platform binary distribution.
- The full development record is retained in [CHANGELOG.md](../../CHANGELOG.md).
  [Dependency and release policy](../ci-release-policy.md) documents the
  enforced gates and publication controls.
