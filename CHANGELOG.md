## [Unreleased]

### Added

- Gateway panel (1) now probes the loop-tick witness socket (`state/gateway.loop-tick.<pid>.sock`, or its 127.0.0.1 TCP port on Windows) and shows an authoritative `alive` badge when the gateway's own loop answers — the heartbeat file has been written off-loop since #90502, so freshness alone no longer proves the loop dispatches. Escalation to `wedged` requires silence across consecutive probes plus a stale heartbeat, mirroring upstream's sustained window; a heartbeat that predates the witness key renders as `legacy heartbeat`, where staleness alone is evidence. The detail view explains which witness decided the verdict.
- Gateway panel (1) shows crash forensics: `previous exit unclean` and `suspected OOM` carry flags from the lifecycle sentinel, the respawn-storm ledger (`gateway-starts.log`) as starts-per-2-minutes against the cap with a `respawn backoff` badge, the tail of the `gateway-exit-diag.log` crash ledger (last exit tag, unclean exits in 24h, size with an oversized warning — upstream never prunes it), and stat-only metadata for the event-only companion logs (`gateway-shutdown-diag.log`, `gateway_faulthandler.log`, `launchd-reload.log`), where growth, not absence, is the signal.
- Gateway panel (1) shows web-dashboard attachment from the `state/dashboard_clients.heartbeat` marker (mtime only; a `web client` chip when one attached in the last minute), respawn-storm counts, and per-served-profile mirror URLs synthesized from the default profile's `listener_base` (`Inbound callback URLs on the shared listener`), redacted and suppressed exactly like recorded ingress URLs.

### CI/CD

- Hardened the whole pipeline per the consolidated CI/CD audit. Nix now proves buildability: the flake derives its version from `pyproject.toml` (single source of truth), declares `checks` outputs that build the package, run its pytest suite, and smoke the installed CLI, and CI builds `.#hermesd` on Linux and macOS instead of merely evaluating. Published runtime requirements are exact pins matching `uv.lock` (`rich==14.3.3`, `pyyaml==6.0.3`, `pydantic==2.13.4`), enforced against wheel metadata by `scripts/check_wheel_pins.py`; the pydantic upgrade itself was validated on hermesd's own full Python 3.11–3.14 matrix, mypy, and snapshot/threading surfaces before landing (decision and evidence in `docs/dependency-decisions.md`).
- CI now separates lint/format/types into a `static` job, dependency auditing into a `security` job (per-interpreter, marker-aware), and keeps the test matrix to behavior; a composite `locked-env` action defines toolchain setup once so CI and the publication workflow cannot drift, with release builds keeping uv caching disabled to preserve the publication trust boundary.
- Docker and Nix jobs are classified by changed inputs on pull requests — always including application source and package metadata — behind an always-reporting **CI gate** that fails on any non-success outcome of expected work (failure, cancellation, or skipped-but-expected), giving branch protection one stable required check.
- Release eligibility is mechanically enforced: a `release-eligibility` job requires the exact tagged commit to carry a completed, successful CI gate run and refuses to publish on missing, failed, cancelled, stale, or in-progress validation.
- Security validation runs on a schedule: a weekly workflow re-audits the locked environment on every supported Python and scans the exported lockfile directly (dev toolchain included) without installing, with pip-audit outcomes classified so scanner failures retry once and then fail as infrastructure errors rather than looking clean; pull requests additionally pass a SHA-pinned dependency-review gate (moderate severity blocks, missing snapshots retried visibly, read-only permissions).
- Installed-artifact testing now covers runtime behavior: `scripts/installed_smoke.py` runs the installed wheel/sdist from outside the checkout against synthetic Hermes-home fixtures (text/JSON snapshots, panel selection, missing-data handling, the read-only invariant, `py.typed`, exact dependency pins, and metadata/version agreement); smoke environments live under `$RUNNER_TEMP` instead of the repository; the Docker checkpoint smoke goes through the public CLI with a synthetic checkpoint repo instead of a private helper; Nix builds run the package tests on two OSes; test runs use concise `-q -ra --tb=short` output and upload JUnit plus coverage data on success and failure alike; Dependabot groups routine minor/patch action updates while majors stay individually reviewed.
- CI/CD and release policy is documented canonically in `docs/ci-release-policy.md`, which `AGENTS.md`, `CONTRIBUTING.md`, and the README link to instead of restating; it also records the retained release re-validation, the disabled release-cache trust decision, the local-build-only container posture, and the manual release checks CI cannot replace.

### Added

- Added a separate, root-scoped Desktop plugin inventory. It reports the bounded presence of regular `desktop-plugins/*/plugin.js` entries without reading JavaScript or claiming that a plugin is loaded or enabled, and keeps truncation and source-health state distinct from the Agent Plugins inventory.

- The Operations panel now reports the API server's durable run reservations, which had no reader anywhere in hermesd. A new `api_runs` health source opens `runs_idempotency.db` — PROFILE-scoped, exactly where upstream resolves it (`get_hermes_home()/"runs_idempotency.db"`, `gateway/platforms/api_server_run_idempotency.py:67`, permissions tightened to 0600 including the `-wal`/`-shm` sidecars at `:116-124`) — through the shared read-only connector, so a store with a WAL sidecar is copied to a private temp dir before it is opened and nothing is ever written back to `~/.hermes`. The section is labelled **Retained API Run Reservations** rather than "API Runs" because the table is a replay window and not an activity ledger, and the panel says why on every pass: `_prune_stale_terminal_locked` (`:168-186`) runs inside *every* `reserve` and `lookup` and deletes an aged row **only once its stored run status is terminal** (`TERMINAL_STATUSES = {completed, failed, cancelled, interrupted}`, `:17`), while long room runs push `retention_until` out (`extend_retention`, `:205-214`; `api_server_runs.py:56-61,222-232`) — so **an empty store is not evidence that the API was idle**. Nor is a present store proof the gateway is using it: when the file cannot be opened upstream logs "Run idempotency storage is unavailable; falling back to process memory, so replay will not survive a restart" and connects `":memory:"`, setting `_db_path = None` so `durable` is False (`:63-84`), and that capability is advertised only over HTTP (`api_server.py:2276`, `_idempotency_capabilities` `api_server_runs.py:108-113`) and never written to disk — hermesd therefore cannot detect the fallback and does not pretend to. An empty-but-present store renders `no reservations retained — not evidence that the API was idle` instead of a blank table. What is reported: store size, reservation count, a distinct-`scope` count, acknowledged and pid-recorded counts, how many rows are already past `retention_until`, the newest `updated_at` and oldest `created_at` as ages against the injected clock, and a bounded eight-row table of run id, status, created/updated ages, retention remaining or overdue, and ownership. Statuses are allowlisted against the vocabulary upstream actually sets — `queued` (`api_server_runs.py:475`), `running` (`:705`), `waiting_for_approval` (`:592`), `stopping` (`:871`) and the four terminal ones — and anything else renders as `unknown` rather than being dropped or guessed, because the store outlives the enumeration. `status_json` is parsed no further than that single word under a 16 KiB cap, and `fingerprint`, `idempotency_key` and `scope` are never selected: the tenant scope appears only as `COUNT(DISTINCT scope)`. `owner_started` is deliberately *not* carried as a timestamp — upstream fills it from `gateway/status.get_process_start_time` (`api_server_runs.py:81-87`), which returns `/proc` ticks on Linux and psutil centiseconds elsewhere, so it is same-host comparable only and this branch has already been bitten by exactly that unit split (`runtime/active_sessions.json` stores epoch seconds while `gateway_state.json` stores centiseconds); hermesd reduces it to `identity recorded` / `identity unverified` beside the pid and its liveness, so a pid that cannot be distinguished from a recycled one is labelled as such. Columns added by upstream's `_MIGRATIONS` (`:29-34`) are gated on a `PRAGMA table_info` set read once per connection, and every column is selected **by name** rather than positionally, because column order is not stable across databases. As with the other database sources, an absent or unreadable store reports `db_present=False` without failing the source, while one that disappears, corrupts or is replaced by an unsafe symlink after a good read raises so the panel keeps its last-good values and `api_runs` appears in `health.failed_sources`.
- The Operations panel now reports hosted-room coordination, which had no reader anywhere in hermesd. A new `hosted_rooms` health source opens `shared-state.db` — **ROOT-scoped even under `--profile`**, and deliberately *not* the master `state.db`: `default_db_path` (`gateway/hosted_rooms.py:398-414`) walks a profile home back up to the shared root, because "pointing profile gateways at the master session store makes every profile process a long-lived writer on state.db — the recurring multi-writer corruption vector observed across a 6-gateway fleet", a choice upstream pins with its own `test_default_db_path_never_names_the_master_session_store` (`tests/gateway/test_hosted_rooms.py:1344-1364`). That is not a hypothetical distinction: the live `~/.hermes/state.db` *also* contains `hosted_rooms`, `hosted_room_events`, `hosted_room_links`, `hosted_room_peer_reservations`, `hosted_room_remote_runs`, `hosted_room_retired_ids`, `hosted_room_revoked_grants` and the same policy tables, all with **zero rows** and no DDL anywhere in `hermes_state_common.py` — legacy leftovers, so reading them would report a dead table as the coordination state. hermesd never opens `state.db` for this source, and three tests pin it: a populated `state.db` with no `shared-state.db` reports an absent store, a populated `state.db` beside a populated `shared-state.db` yields only the latter's rooms, and a `sqlite3` trace callback asserts every `hosted_room*` statement ran on a `shared-state.db` connection. The section reports active versus disbanded room counts against upstream's own ceilings (`MAX_ACTIVE_ROOMS = 256`, `MAX_DISBANDED_ROOM_TOMBSTONES = 512` retained 90 days, `MAX_EVENTS_PER_ROOM = 50_000`, `:33-41`); a bounded eight-room table of id, name, member count, authority epoch, revision, `latest_seq` (derived as `next_seq - 1`, never stored beside it), accounted `event_bytes`, age and active/disbanded state; the event count with `SUM(hosted_rooms.event_bytes)` and the newest event age; retired-id and revoked-grant counts; link and remote-run counts; and peer reservations split live / expired / revoked, where revoked wins over expired so the three buckets partition the table and the total is derived from them. Event `kind` is the one string that leaves `hosted_room_events`, because it is a closed protocol vocabulary rather than content (`:49-57`) — and it is histogrammed by a `WHERE kind IN (…)` over the seventeen recognized values, so an unrecognized kind is never selected at all and surfaces only as a derived `unknown` complement that keeps the histogram summing to the true event count. **The rest is content-free by construction**, and the contract is pinned structurally as well as behaviourally: `hosted_room_links.grant`, `catalog_json` and `target_url` (a target URL may embed a credential), `hosted_room_events.payload_json` and `actor_json`, `hosted_room_revoked_grants.scope_key` and everything in the `hosted_room_policy_transcript*` conversation tables are never selected; `member_count` is the *length* of `members_json`, parsed under upstream's own 128 KiB `MAX_MEMBERS_JSON_BYTES` cap and reported as 0 past it, so a runaway blob costs a length check and its member identities never leave the file. One test walks the new models' field names and types and fails if any non-`int` field mentions a grant, catalog, payload, actor, scope key, target URL, transcript, body or member list — so the contract is a property of the schema, not of what the reader happens to do today — and a second plants a distinct canary in every excluded column plus the two transcript tables and asserts none of them reaches `model_dump(mode="json")`. A third asserts no issued statement names `policy`, `payload_json`, `actor_json`, `catalog_json`, `target_url`, `scope_key` or a bare `grant`. Display truncation never changes a computed count: every count is a whole-table aggregate, the room list is capped at eight, and hitting the cap sets `rooms_truncated` and renders `showing 8 of 12 — the counts above cover the whole table`. `event_bytes` and `authority_epoch` were added to `hosted_rooms` by upstream's `_LEGACY_COLUMN_DDL` (`:340-348`), so both are gated on a `PRAGMA table_info` set read once per connection and every column is selected by name, never positionally and never with `SELECT *`; a room table missing its `room_id` primary key raises rather than reporting an empty list beside a non-zero count. As with the other database sources, an absent `shared-state.db` reports `db_present=False` without failing the source, while one that disappears, corrupts or becomes an unsafe symlink after a good read raises so the panel keeps its last-good values and only `hosted_rooms` appears in `health.failed_sources` — the rest of the Operations panel stays fresh.
- The Operations panel now reports the database-recovery evidence hermes-agent's own repair code leaves beside `state.db`, none of which had a reader before. A new `db_recovery` health source scans the profile home once — bounded at 200 entries, symlink-confined, and testing each entry's *name* before it costs a syscall — and reports four artifact families: the cross-restart attempt ledger `state.db.repair-attempts.json` (`_repair_ledger_path`, `hermes_state_repair.py:317-318`) with its `failed_attempts`, its `last_attempt` as an age, and whether the recorded budget of `_MAX_PERSISTENT_REPAIR_ATTEMPTS = 3` (`:48`) is exhausted; the settled forensic backups `state.db.malformed-backup-<stamp>[_<seq>]` (`_backup_db_file`, `:503-513`, retained to three by `_prune_malformed_backups`, `:443-451`) with count, total bytes and newest age, where the bytes include each settled copy's present `-wal`/`-shm`/`-journal` sidecars that upstream prunes with it, but exclude a sidecar whose main copy is already gone; the retired-WAL generations `state.db.retired-wal-<utc stamp>-<pid>[-n]/` (`RETIRED_GENERATION_DIR_SUFFIX`, `hermes_state_dbfile.py:228`, `capture_retired_wal_generation` `:334-425`) with the newest one's `captured_at`, `trigger`, `wal.bytes` and `main.mode` read from its `manifest.json`; and the `state.db.repair.lock` / `state.db.auto-maintenance.lock` files as presence booleans. **Presence and metadata only, and that limit is pinned by test rather than left to intention:** the reader never opens `state.db` (a test counts `Path.open` calls against it and asserts none) and never hashes or connects to it (a test makes `hashlib.sha256`, `hashlib.new` and `sqlite3.connect` raise), so no repair, checkpoint or integrity check is reachable — the live database is ~480 MB and hashing it is exactly the expensive work excluded here. Mid-write artifacts are counted apart from settled ones and never inside them, because presenting an in-progress copy as a completed forensic capture would misreport the recovery record: `.backup-staging-*`, the old `*.incomplete*` spelling (which prefix-matches as a backup, sorts newest, and would otherwise survive pruning forever — `:487-501`) and `.partial` retired generations all get their own **In Progress** row. Three wording rules follow from upstream's behaviour and are stated in the panel on every pass. A *successful* repair deletes the ledger (`ledger_path.unlink(missing_ok=True)`, `:414-416`), so `none — no failed repair recorded` is not evidence the database is healthy and the section says so. `budget exhausted` counts the ledger's recorded failures and deliberately does not recompute the fingerprint `_persistent_repair_attempts_exhausted` (`:487-500`) also matches them against — that fingerprint is a bounded SHA-256 sample of the database hermesd will not read — so the panel cannot tell whether the file changed since, and says that too. And a lock *file* on disk is not a held lock, since `_open_lock_file` opens both with `"a+b"` and never deletes them; the row is labelled `file present, not held`. The ledger's `last_attempt` is `datetime.now().isoformat(timespec="seconds")` (`:428-430`), i.e. naive *local* time, so it gets its own parser instead of the shared naive-as-UTC one, which would have shifted every age by the host's UTC offset; the retired-WAL `captured_at` is `%Y-%m-%dT%H:%M:%SZ` and does go through the shared parser. A present-but-unusable ledger or manifest raises rather than reading as absent, so a torn write — upstream uses a plain `write_text` — fails only `db_recovery` and the panel keeps its last-good values, while a settled generation whose `manifest.json` is missing is still counted with nothing claimed about its contents. `~/.hermes/recovery/` is deliberately not read: it holds operator-made remediation bundles (`config.yaml.before`, `git-status.before.txt`, `repository.bundle`) that no upstream repair code writes, and every artifact here is named after the database file, so it cannot match. The source is PROFILE-scoped and agrees with upstream — the repaired database is `get_hermes_home()/"state.db"` (`hermes_state.py:160`, repair invoked at `:535`) and every artifact is its sibling — pinned by a test that a root ledger is not reported for a selected profile and by one that a ledger symlinked in from a sibling profile is refused.
- The Sessions and Config panels now expose the active-session capacity policy and the lease details behind the registry, which previously stopped at a PID and a liveness verdict. `max_concurrent_sessions` had no reader anywhere in hermesd, so the cap an operator configured was never shown beside the occupancy it caps, and a refusal upstream would have issued with reason `MAX_CONCURRENT_SESSIONS` — naming the holders per surface via `summarize_holders` (`hermes_cli/active_sessions.py:72-101`) — was invisible. It is now read exactly as upstream resolves it: `resolve_max_concurrent_sessions` (`:47-61`) takes the top-level key, else `gateway.max_concurrent_sessions`, and `coerce_max_concurrent_sessions` (`:31-44`) accepts only a positive integer, so `0`, `null`, a fractional float, a boolean, an unparseable string and an absent key all read as *not configured* rather than as a limit of zero — a different statement, since upstream enforces capacity "only when an operator asked for one" (`:524-532`). Panel 5 gains a **Session Capacity** sub-section that always lists both session caps under names saying which resource each governs — **Active-Session Lease Cap** as `4 (max_concurrent_sessions)` or `not configured (unbounded)`, and **In-Memory Live-Session Cap** as `16 (max_live_sessions)` or `not configured (LRU eviction off)` — because the two are unrelated limits and conflating them would misreport capacity: the first is a cross-process lease cap checked when a surface attaches, the second a soft LRU cap that evicts only *detached* in-memory gateway sessions with `end_reason="lru_evict"` (`tui_gateway/session_reaper.py:250-265`) and never a running, pending or live-transport one. A note under the two rows states the distinction on every pass, and panel 2 never renders the LRU cap at all. The Sessions detail view keeps three numbers visibly apart on its Live Surfaces header line — the *configured* capacity (`cap C leases` or `no active-session cap configured`), *observed registry occupancy* (`N registry entries`) and *verified executing activity* (`M verified executing`, counting only identity-verified leases, with unverified and dead listed beside it and never folded in) — plus a fourth, `distinct pids`, because several leases can name one process and occupancy is therefore not a process count; the compact view adds `cap C` / `no cap` and warns once occupancy reaches the cap. Registry occupancy and capacity warnings use the complete valid-entry count from the bounded input, while filtering changes only the visible table rows; when the 200-row retained sample truncates the registry, the panel labels shown versus total entries instead of presenting the sample as complete. Each lease now also carries its own metadata from `_lease_entry` (`:421-439`): `lease_id`, `track_liveness` (set only for desktop-surface leases, `tui_gateway/session_lifecycle.py:33-38`), and `started_at`/`updated_at` as ages against the injected clock — recomputed on every pass and never stored in the mtime-keyed file cache, which holds only the raw JSON. A derived `lease_renewed` marks the one thing that moves `updated_at` past acquisition, `transfer_active_session` (`:554-601`), and renders as `moved`, so a transferred lease's acquisition age is not mistaken for the age of the session it now holds; a stamp that is not the epoch float upstream writes — an ISO string, `null`, a non-positive number — reads as no age at all rather than as January 1970. There is no expiry or renewal field to report, because a lease lives until it is released (`:536-551`) or pruned when its owner is provably dead (`:348-360`). The registry's resolver is unchanged and its consequence is now recorded in `.codex/rules/source-ownership.md`: hermesd reads the selected profile's registry, matching upstream's `_state_path` (`:164-168`), while `release_orphaned_leases` (`:660-687`) sweeps the root home *and* every profile home, so the occupancy shown is one registry's and not the install's.
- Sessions now surfaces the durable half of the compressor's anti-thrash guard, and panel 2 turns it into an active-recovery warning. hermesd read exactly one compression column (`compression_failure_error`) and rendered it as up to ten failing sessions, so a session the compressor was *actively refusing to compact* looked identical to one that had failed once and recovered. Four more `sessions` columns are now read — `compression_failure_cooldown_until`, `compression_fallback_streak`, `compression_ineffective_count` and `compression_recovery_deadline` (`hermes_state_common.py:375-379`) — and the Warnings section gains a `recovery — cooldown 45s left, anti-thrash probe in 4m, fallback streak 2, ineffective 3` line per session, with a `⚠ N compression recovery` marker in the compact view. Liveness is decided against the injected clock (`state.collected_at`) rather than at collect time, because the `sessions` source is memoized on row identity: a countdown baked into the model would have frozen until the database next changed. The comparisons mirror upstream exactly — a cooldown counts only while `cooldown_until > now` (`get_compression_failure_cooldown`, `hermes_state_compression.py:329-335`) and a recovery deadline only while it is armed and in the future (`context_compressor.py:2558-2563`) — so an *expired* timer renders as nothing at all instead of as a warning about a clock that has already run out. `0` and NULL both mean "disarmed" for the deadline (`set_compression_recovery_deadline` persists `normalized or None`, `:413-431`) and are normalised to `None` at the read boundary, because surfacing a stored `0` as an epoch would have rendered as January 1970. Both counters stay tripped-state-only: a non-zero strike count with no armed timer is deliberately **not** reported as active recovery, since upstream re-probes on the deadline, not on the count. No compression or model threshold is shown anywhere in the section — the values in `config.yaml` are configured policy, not the effective runtime threshold the compressor evaluated, and hermesd cannot observe the latter. Nothing here reads conversation content: all four fields are counters and timestamps on the session row, and the section says so on every pass. Older schemas keep working through the existing `PRAGMA table_info` availability filter, which now lists the four columns as optional, and a TEXT value in a REAL column coerces to "no deadline" instead of failing the whole `sessions` source.
- The MCP schema cache now reports whether each entry would actually be served, not just that it exists. `cache/mcp_schema_cache.json` was summarised as names, a count and a file age, so a cache that looked fully populated could be one hermes-agent never reads from. Each entry is now assessed against upstream's own validity rule (`get_cached_entry`, `tools/mcp_schema_cache.py:59-73`) and reported as `valid`, `expired` or `unassessable`, rolled up as an `Entry validity` row and detailed one line per server — `codegraph  expired — 0ms ttl elapsed 12h ago  fp 7df47d93` — with a `1 expired` / `2 unassessable` marker in the compact view. Expiry uses the entry's own `written_at`, never the file mtime, which advances on every unrelated write-through; the arithmetic is reproduced exactly, including the two cases that read as bugs but are the contract: `ttl_ms: 0` is **always** expired because `age >= 0` holds for any real clock, and an entry with no numeric TTL **never** expires. Upstream needs both `ttl_ms` and `written_at` to be numeric before it can expire anything, so a TTL recorded without a write stamp stays valid, and `isinstance(True, int)` is mirrored rather than "fixed" so a JSON `true` in a numeric slot behaves here as it does there. `unassessable` covers a non-mapping entry and a missing, empty or non-string `fingerprint` — shapes upstream would also refuse — and carries the reason. The rollup counts every entry in the file while the rendered list stays bounded at 20 with a `(+N more)` marker, so a display cap can never change a reported count. Nothing from `tools`, `utility_tools`, `inputSchema` or `cache_scope` is copied into state: those payloads are opaque, unbounded, and a tool manifest can carry a default credential, so a test asserts six canary strings planted across all of them never reach `state.model_dump(mode="json")`. **No configuration-compatibility verdict is claimed.** Upstream's first test is `entry["fingerprint"] != config_fingerprint(config)`, but that `config` is not the `config.yaml` hermesd can read: `_load_mcp_config` (`tools/mcp_tool_config.py:322-345`) hashes the `${VAR}`-interpolated block, resolved through the active profile's secret scope and `${workspaceFolder}` (`:244-259`), out of a `load_config()` that is already `DEFAULT_CONFIG + config.yaml + managed scope, env-expanded` (`hermes_cli/config.py:1965`), and then merges in plugin-provided portable servers that appear in no YAML at all (`:307-320`). Recomputing the hash from raw YAML would report a mismatch for every server whose `command`, `args` or `url` carries a placeholder, and hermesd can neither resolve secrets nor import the loader that would. The recorded fingerprint is therefore exposed as an 8-char prefix for an operator to compare, `MCPCacheEntryState` has no `configuration-mismatched` member to claim, and the section states on every pass that a valid entry does not prove credentials work or that the server is reachable, that an expired one is not an error because the next call re-probes it, and that the fingerprint shown is the cache's own record rather than a comparison hermesd performed. Expired entries are deliberately styled dim rather than as errors for the same reason.

### Fixed

- Fixed Agent Plugin compatibility: provider-kind auto-detection now runs only when `kind` is absent, while explicit null, blank, non-string, and unknown values remain standalone as upstream treats them. Portable v1 manifests now mirror all upstream load-blocking field validation, including author, project links, licensing, keywords, and extensions.
- Migration verification now requires the supported version-1 manifest schema, a valid default profile record, and well-shaped secondary profile records. Malformed or unsupported manifests remain visible as intent metadata but can no longer produce a verified migration verdict.
- Active-session capacity now uses the complete valid-entry count from the bounded registry input, independently of filtering and the 200-row retained display sample. The Sessions panel labels shown versus total entries and reports truncation, so filters no longer suppress a registry-wide at-capacity warning.
- Gateway, Cron, Skills / Integrations, Sessions, and Operations detail views now share a whole-render viewport, making lower sections reachable with `j`/`k` and `g`/`G` at ordinary terminal heights. Resizing and filtering re-clamp the live position, while copy and snapshot rendering remain non-mutating; direct Skills panel rendering retains its existing 20-row paging API.
- Unreadable cron catch-up and ticker-error markers now fail the cron source and preserve last-good state instead of clearing observed counters or errors. Read-only SQLite snapshots likewise refuse unsafe, unreadable, symlinked, or dangling `-wal`/`-shm` sidecars before immutable fallback, preventing checkpoint-old false-zero results while still allowing genuinely absent sidecars.
- Expired API reservation counts are now labelled as rows past their retention deadline. They may include terminal rows awaiting a later request-triggered pruning pass, so the panel no longer invents a missing terminal status.

- The read-only SQLite helper's `-wal` sidecar probe now fails the source instead of silently downgrading. `_connect_readonly_sqlite` chooses between a temporary WAL snapshot and a direct `mode=ro&immutable=1` open, and it probed for the sidecar with a bare `Path.exists()`. From Python 3.14 `exists()` also swallows `EACCES`, so an unreadable sidecar read as *absent* and the connection fell through to `immutable=1` — which serves checkpoint-lagging data as though it were current, the false-empty class of failure every other reader here raises on. It now uses `_exists_strict`, matching `db.py`'s shared `state.db` connection and the guarantee this changelog already claimed for it. This helper backs the kanban, cron, operations, response-store, projects, verification-evidence, hosted-room and API-run reads, so the exposure was wide even though only Python 3.14 could trigger it.
- `max_live_sessions` was read from the top level of `config.yaml` only, so a cap configured under `gateway.max_live_sessions` rendered as unset and the Config panel silently omitted a limit the gateway was enforcing. It now honours the same `gateway.*` fallback upstream's own reader uses (`_max_live_sessions`, `tui_gateway/session_reaper.py:237-247`) and reproduces its asymmetry with the lease cap rather than unifying the two: the LRU cap falls back on a *null value* (`raw is None`), so an explicit top-level `max_live_sessions: null` does reach `gateway.*`, while `resolve_max_concurrent_sessions` falls back on key *presence*, so a top-level `max_concurrent_sessions: null` shadows the gateway section. Both readings are pinned. An unset `max_live_sessions` still reads as `0`/off rather than as the `16` in `config_defaults.py:42`, which is what upstream effectively does: `_load_cfg()` is documented as `load_config_readonly` *minus* the DEFAULT_CONFIG merge (`tui_gateway/server.py:1169-1176`, "callers treat a missing key as 'unset'"), so `_max_live_sessions()` returns 0 for a `config.yaml` that never sets the key and `_enforce_session_cap` evicts nothing.
- Plugin provenance is now read from the installer's own sidecars instead of being absent, and the two records it keeps are deliberately not collapsed into one. `~/.hermes/plugins/.install-metadata.json` (`hermes_cli/plugins_cmd.py:425-446`) is a single JSON object keyed by **manifest name** — not directory name, which `_sanitize_plugin_name` derives separately — whose entries are written at `:670-672` as `{"pinned": requested_revision is not None, "revision": installed_revision, "source": source}`; hermesd reads it once per pass however many plugins were found, and mirrors `pinned_revision()` (`:449-454`) exactly including the `is True` identity check, so a truthy string in that field is not reported as a pin. `<plugin_dir>/.hermes-catalog.json` (`hermes_cli/plugins_cmd_catalog.py:24,62-85`) records the catalog entry that was *reviewed* — `catalog_name`, `repo`, `sha`, `tier`, `installed_at` — and, as upstream's own `read_catalog_sidecar` does, an absent or corrupt sidecar means "not a catalog install" rather than an error or a guess. The two disagree by design and that disagreement is the point: `install_catalog_entry` (`:108-118`) installs at `ref or entry.sha` and then writes the sidecar from the entry, so an explicit `--ref` leaves the catalog sha describing a commit that is not on disk while the install metadata records the HEAD that is. The Skills panel's new **Provenance** column therefore renders upstream's own two annotations as separate tokens — `catalog:<tier>@<sha8>` (`:88-93`) and `git@<sha8>` / `git pinned@<sha8>` (`plugins_cmd.py:457-459`) — adds a `⚠ drift` marker when the two full 40-hex SHAs differ, and drops the redundant second token when they agree, because the catalog sidecar alone is not evidence of what code is installed. A SHA that is not a full 40-hex commit is reported as no revision at all rather than rendered as one, so a corrupt sidecar can fabricate neither a pin nor a drift. `source` and `repo` are re-redacted through `_redact_secret_url` at the data boundary even though upstream scrubs credentials before writing (`_scrub_git_url`, `:513-521`), with the `#subdir` fragment a monorepo install appends (`:524-526`) preserved; a test asserts a credential-bearing URL never reaches `state.model_dump(mode="json")`. A new **Declares** column carries the manifest's `requires_hermes` gate and a `caps:N` count of declared capabilities, worded as declarations because that is all they are: upstream evaluates the version gate against the running build at load time (`plugins_manifest.py:412-419`) and gates every capability behind an explicit grant under `plugins.entries.<id>.granted_capabilities` (`plugin_capabilities.py:44-46`), neither of which hermesd can observe. The count is the full declared one, not the length of the display-bounded list, so capping that list cannot change what the panel reports, and declared ids are preserved as written rather than filtered to the ones this build recognises — dropping an unknown id is fail-closed for a consent screen, but an unrecognised declaration is exactly what a dashboard should show. A note under the table states on every pass that hermesd never imports plugin code, so none of activation, provenance or declarations is evidence a plugin loads. Both sidecars keep the `skills` source's existing ROOT resolver, and `.codex/rules/source-ownership.md` records the consequence: under `--profile`, a selected profile's plugins *and* their install provenance are invisible, exactly as its `plugins/` already was.
- Plugin discovery now covers every manifest format and directory shape hermes-agent accepts, rather than only a flat `plugin.yaml`. Upstream's `scan_directory` (`hermes_cli/plugins_discovery.py:102-131`) takes the first of `plugin.yaml`, `plugin.yml` and a portable `plugin.json` that exists — an order repeated at `plugin_dev.py:154`, `plugins_cmd.py:265-271`, `config.py:3753` and `config_migrations.py:277-281` — and walks two shapes: a flat `<root>/<name>/` keyed by its manifest `name`, and a category `<root>/<cat>/<name>/` keyed by the *path* `<cat>/<name>`, which is the spelling `plugins.enabled`/`plugins.disabled` actually contain. hermesd read only the flat shape and only `plugin.yaml`, so a `.yml` install, a portable Agent Plugin and every category plugin were invisible — and a category plugin was invisible twice over, since even a hand-copied manifest under a category directory was gated on the wrong key. A manifest-less directory is still not a plugin: it is a category, recursed into exactly one level, and past that upstream's depth cap stops the walk, so `plugins/a/b/c/plugin.yaml` is not discovered. A conflicting pair is resolved by precedence **and reported** rather than silently: the winning filename is recorded in `manifest_file` with its reader in the derived `manifest_format` (`yaml`/`portable`), the losers in `manifest_shadowed`, and the detail view lists the conflicts under the table with their true count and a `(+N more)` marker. Portable manifests are validated against the v1 Agent Plugins schema and its name grammar before being believed (`hermes_cli/agent_plugins.py:16,24,87-118`), and only `name`/`version`/`description` are carried over because that is all `portable_plugin_manifest` keeps (`plugins_manifest.py:422-437`) — a `plugin.json` declaring `kind`, `capabilities` or `requires_hermes` is not read as declaring them, and no `__init__.py` scan applies, since upstream never sets a kind on the portable path. Any format that is present but unusable degrades to `unknown` with a reason instead of vanishing, and a malformed manifest still fails only itself rather than the whole `skills` source. Two divergences are deliberate and pinned: hermesd refuses a *symlinked* manifest including the symlinked `plugin.json` upstream explicitly accepts, because that confinement check is what stops a plugin tree from steering a read outside `~/.hermes`; and it derives a flat plugin's key from the manifest `name` alone, ignoring any `key:` field the manifest declares — `parse_manifest_file` (`plugins_manifest.py:468`) never reads one, so `plugins.enabled` cannot contain that spelling, and honouring it would have reported a plugin as enabled that hermes-agent refuses to load. The directory walk is budgeted — at most 200 entries examined per directory and 200 plugins retained — and hitting either bound sets `plugin_scan_truncated`, rendered as `⚠ plugin list truncated` in the detail view and a `+` after the count in the compact view, so a bounded sample never presents itself as a complete inventory.
- Missed cron runs and ticker failures are now visible instead of being inferred from a heartbeat alone. Two markers hermes-agent writes into `cron/` had no reader at all. `catch_up_occurrences` is the lifetime counter `_fast_forward_missed_recurring` bumps when a recurring job's `next_run_at` was more than its grace window in the past and catch-up re-anchored it (`cron/jobs.py:2893-2921`); it carries no timestamp and is never reset, so panel 6 renders it as a lifetime total and never as a rate or an age. Upstream's own reader returns `0` for a missing file and for a genuine zero alike (`get_catch_up_occurrence_count`, `cron/jobs.py:1186-1193`) — collapsing precisely the distinction an operator needs, since the write is best effort (`_write_marker` swallows every exception, `:1129-1136`) and is skipped entirely while catch-up is disabled — so hermesd keeps them apart as `Catch-ups: no counter observed` versus `Catch-ups: 0 recorded`. `ticker_last_error` is the reason behind a failing tick, written as `f"{time.time()}\n{message}"` and read with upstream's `len(lines) < 2` torn-write guard mirrored (`:1212-1220`); the message is an arbitrary `f"{type(e).__name__}: {e}"` string that can embed paths, tokens or URLs, so it is redacted through `_redact_secret_text` and capped at 80 chars in the collector, and terminal-control-sanitized at the panel. It is shown with its age, and that age is reported as unknown rather than as a placeholder when the stamp on line 1 did not parse. **Absence of either marker is never rendered as health**, and the detail view says so on every pass: `clear_ticker_error` *deletes* the file on the next clean tick (`:1206-1209`), so a ticker that failed for hours and then recovered leaves no trace, and the catch-up counter does not move while catch-up is off. A recorded error now also escalates an otherwise `ok` ticker to `failing`, because upstream unlinks the marker only on a clean tick (`cron/scheduler_provider.py:438,447`) — without this, panel 6 would print `ok` beside the failure it is displaying; it never escalates `unknown` (no heartbeat means hermesd cannot claim the loop runs) and never downgrades `stale`. The configured policy is surfaced next to the observed counter from `cron.catch_up_missed`, read with upstream's exact cast `_cron_config_number("catch_up_missed", True, lambda value: value is not False)` (`:2908`, `:2615-2624`) — an *identity* check, so only a literal YAML `false` disables catch-up while `null`, `0`, `'no'` and a missing key all leave it enabled; a naive `bool(value)` would report the opposite for each of those, and a test pins all of them. When it is off the panel flags it distinctly, because that is the silent case: `_fast_forward_missed_recurring` re-anchors the schedule and logs a skip *without* recording anything, so runs are dropped and the counter stays flat. Per job, `last_dispatch.kind == "catch_up"` is now labelled `catch-up after missed fire` instead of rendering identically to `late`, matching upstream's own CLI wording (`hermes_cli/cron.py:119`), with an unseen kind passed through sanitized rather than bucketed. The compact view spends a line only on the two current problems — catch-up explicitly off, and a recorded tick error — never on a non-zero lifetime counter. Both markers keep the `cron` source's existing ROOT resolver so `.codex/rules/source-ownership.md` stays accurate for every path that row names; the consequence is recorded there and in the README, namely that under `--profile` a selected profile's own tick failure and catch-up counter are invisible, exactly as its `jobs.json` and ticker stamps already are. A threshold divergence is documented rather than retuned: `hermes cron status` calls the ticker STALLED after ≈200 s while hermesd's last-success window is 600 s, so there is a range where the CLI already says STALLED and panel 6 still says `ok`/`failing`.
- A multiplex-migration manifest is no longer readable as proof that the migration succeeded. `~/.hermes/gateway_migration.json` had no reader at all, so panel 1 could say nothing about `hermes gateway migrate --multiplex` — and the obvious thing to build from that file would have been wrong. Upstream writes the manifest *inside* the per-secondary loop (`hermes_cli/gateway_migrate.py:543-544`), before `_write_multiplex_flag` (`:545`) and before `_restart_default` (`:549`), rewrites it byte-identically at `:546`, and then never touches it again: neither the verified path (`:553-557`) nor the applied-but-unverified path (`:558-561`) writes it, and the shape built at `:528-533` has no `completed`/`verified`/`outcome`/`finished_at` field. A manifest on disk is therefore indistinguishable between mid-flight, crashed after one secondary, applied-but-unverified and fully verified; `migrated_at` means "the attempt began at"; and because `rollback_migration` deletes the file on success (`:604-608`), absence means "never migrated OR successfully rolled back". hermesd now keeps three things apart instead of collapsing them: **recorded intent** (version, `flag_was`, the recorded homes/services, and `migrated_at` — always labelled `Started:` and never rendered as a bare age), **intermediate progress** (flag flipped? default gateway live? a live served record? which recorded profiles does it cover?), and one **verified current topology** verdict. That verdict is a predicate over artifacts hermesd can actually read — manifest present with a valid supported version-1 schema AND `gateway.multiplex_profiles` on AND the default gateway live AND the live `served_profiles` covering `{"default"} ∪ {manifest secondaries}` — and renders as `● multiplexed (verified)` or `⚠ migration unverified` plus the specific missing evidence (`the default gateway is not live`, `no live gateway recorded a served-profile set`, `not in the live served set: coding`, …). The liveness clause is load-bearing precisely because upstream's `recorded_served_profiles()` returns `None`, not `[]`, when the gateway pid is dead (`hermes_cli/gateway_multiplex_served.py:28-38`). The base `gateway` source is also an explicit freshness dependency: if it falls back after a corrupt read, `migration` is marked degraded and keeps its own last-good verdict instead of checking a newly written manifest against cached served profiles; a fresh later pass re-evaluates immediately. The flag is read the way upstream's *reader* reads it (`:203-215`) — ORing the stale top-level `multiplex_profiles` alias with the nested key rather than matching the writer, which pops the alias — and since that reader first consults an environment override hermesd cannot see, every verdict is labelled "as recorded in config". The words "migrated" and "migration complete" appear nowhere in the panel, pinned by a test over both verdicts. The section folds into panel 1 beside **Updates** rather than becoming a new panel; it is its own `migration` source, so a torn manifest (upstream writes with a plain `write_text`, not atomically) degrades only itself and keeps its last-good verdict while the gateway beside it stays fresh. "Present but unreadable" is distinguished from "absent", the retained secondary list is capped so an untrusted manifest cannot grow it (and a truncated list can never verify), and a recorded `home` value is never resolved — the reader module has no path type at all, because upstream's rollback builds `Path(rec["home"])` straight from this file (`:594`) and an untrusted manifest must not be able to steer a hermesd read. Two limits are documented rather than hidden: `migrated_at` is the only local-time, uncolonned-offset stamp hermesd reads (`+0200`, which `datetime.fromisoformat` accepts from Python 3.11 — the pinned floor — while every other source writes UTC), and upstream verifies against every profile in its *plan* (`:551-552`), which includes profiles that never had a standalone gateway and so are absent from the manifest, making hermesd's expected set a subset of upstream's and its verdict correspondingly weaker. Finally, `maybe_auto_migrate_after_update()` (`:651-665`) can create a manifest during a `hermes update`, so the migration and update-receipt sections can both light up on one tick; they are separate claims, and a failed update receipt does not overturn a topology the live artifacts verify.
- Gateway shared-listener routing and ingress are now surfaced instead of being flattened or dropped. `gateway_state.json` keys a served profile's adapter as `<profile>:<platform>` (`gateway/run_adapters.py:1048`), and hermesd passed that key through verbatim as the platform name — so a multiplexed install rendered a platform called `dev:telegram`, with no profile grouping and no way to tell two profiles serving the same platform apart. Keys are now split against the grammar upstream validates *unconditionally* before projecting a status key anywhere (`hermes_cli/web_routers/status.py:122-127`, whose stated reason is that a failed config-set load must not fail open into projecting arbitrary keys from a process-local JSON file): a valid key yields `PlatformStatus.profile` plus the platform part in `name`, while a key that fails the grammar stays verbatim in `name` with an empty `profile` rather than being split. The detail table gains a **Profile** column and the compact strip renders `dev/telegram`. `ingress_url` was never read at all, despite being the value a user pastes into a vendor console; it is now recorded per platform with upstream's suppression rules mirrored exactly — nothing is kept unless the process that wrote the state file is still live, and falsy values or adapter states of `fatal`/`disconnected`/`stopped` are also suppressed (`hermes_cli/gateway_multiplex_served.py:46-70`, plus the liveness rule `hermes_cli/web_routers/messaging.py:263` applies to plain keys too) — and it is redacted through `_redact_secret_url` at the data boundary, never in a panel, because an ingress URL is exactly the shape that carries userinfo or a secret query parameter. A live fallback PID still proves the gateway is running and is shown as its PID, but after the recorded-writer probe fails it cannot authorize that writer's served-profile list or ingress URLs — even if the numeric PID is the same, because it may have been reused; the unchanged record stays non-authoritative on later polls and becomes current only after the replacement writes fresh state. A new **Shared-Listener Ingress** section presents the values as *recorded information*: it says outright that hermesd never requests these URLs, and a bare path (`/p/dev/telegram/webhook`, which is what `publish_shared_ingress` records when the default profile has no live listener yet, `gateway/platforms/shared_ingress.py:72-95`) is flagged as such instead of being rendered as an endpoint. `served_profiles` also stops collapsing its tri-state: absent, unparseable and explicitly-empty all became `[]`, so "the live gateway serves nobody else" — which upstream treats as authoritative — was indistinguishable from "nothing was recorded". `GatewayState.served_profiles_recorded` now carries that distinction, gated on state-writer liveness rather than mere replacement-process liveness, while the names an old writer left behind are kept and labelled `(record, writer not current)` rather than presented as the current topology. A served profile writes no `gateway_state.json` of its own (`gateway/status.py:917-921,966-970`), so under `--profile dev` the root file's `dev:<platform>` entries are the only evidence of its routing.
- Profile-scoped database readers now confine to the selected profile's home rather than to `~/.hermes` as a whole. `_with_projects`, `_with_verification_evidence` and `_read_state_db` resolve their target through `profile_path()` but checked containment against `root_home`, so a path that landed in a *sibling* profile (`profiles/other/projects.db` while `--profile coding` was selected) satisfied the check and was read: the correct invariant is the one `_summarize_profile` already used, containment against `profile_home`. All three now confine against `profile_home`. In practice the reachable escape route was already closed by the adjacent `is_symlink()` refusal and by `profile_path()` re-validating profile confinement on every call, so this is a narrowing of the accepted set rather than a change in observable behaviour for a well-formed home — but the check now states the invariant it is meant to enforce, and root mode is untouched because there `profile_home is root_home`. Tests pin both directions: a resolver handing back a sibling profile's paths is refused by all three readers, and a root-mode `projects.db` / `verification_evidence.db` still reads.
- Active-session liveness now verifies process identity instead of trusting a bare PID. `runtime/active_sessions.json` records `process_start_time` alongside each `pid`, but hermesd checked only `pid_exists`, so a reused PID made an obsolete registry entry look alive. Liveness is now a three-state `ProcessLiveness` (`live` / `dead` / `unverifiable`): a start-time mismatch means the PID belongs to a different process and the recorded one is gone, while a start time that was never recorded or cannot be observed on this host is reported as unverifiable rather than silently counted as live. `ActiveSurface.alive` is now derived from that verdict, so the two cannot disagree. Because hermesd has no `psutil` dependency, start times come from `/proc/<pid>/stat` field 22 on Linux — anchored on the final `)` so a command name containing spaces or parentheses cannot shift the field — and elsewhere from a single bounded `ps -o lstart=` call covering every PID at once rather than one subprocess per surface per tick. `lstart` reports whole seconds against the registry's fractional stamp, so identity is matched within a 2-second tolerance; on the maintainer's machine all 8 registry entries drift 0.21–0.75 s, which exact equality would have misreported as 8 dead sessions. Note the two identity sources use different units — this registry records epoch seconds while `gateway_state.json` records centiseconds — and are never compared to each other. The compact header no longer labels registry entries as live: it shows `N surface(s)` plus identity-verified `M live` and `K unverified` counts, and the detail table renders `unverified` distinctly instead of as `live`.
- Cron statistics are now qualified as *recorded* attempts rather than presented as complete history. hermes-agent prunes terminal executions to `MAX_TERMINAL_EXECUTIONS` (1000) records keeping the newest by `finished_at`, and never prunes in-flight rows, so the aggregates hermesd renders have always described the retained table — not every attempt that happened. The detail view now exposes the retained total and terminal counts, the observed span of `claimed_at`, and a warning when the terminal count reaches the cap. The warning is deliberately qualified: reaching the cap proves older terminal rows were dropped but says nothing about whether a particular 24h window is complete, and on the maintainer's machine the retained 1000 records span roughly 21 days, far more than the window they qualify. `retention_cap` reads as `0` when the table could not be read at all, which is distinct from an empty one. This is a semantics and wording fix; the earlier 500-row aggregation limit is a separate, already-fixed defect.
- Cron execution success and delivery outcome are no longer conflated. The executions reader selected only the original columns and ignored `delivery_outcome`, `scheduled_instant`, `handoff_pending`, and `handoff_started_at`, so a run that completed with its notification suppressed was indistinguishable from one that was actually delivered — on the maintainer's own machine all 47 executions in the last 24 h were `completed` *and* `suppressed`, which the old counters rendered as a clean `47✓`. Delivery now has its own indicators: per-run `delivery_outcome`/`scheduled_instant`/`handoff_pending` on each recent execution, a **Delivery** column in the Recent Executions table, and a **Delivery Outcomes (24h)** section counting each recorded outcome verbatim per job with unrecorded rows and pending handoffs kept separate. Outcomes hermesd has never seen are preserved as written instead of being bucketed, and the retained vocabulary is bounded per job. The newer columns are read column-aware, so an older schema reports `delivery_tracked: false` and renders nothing rather than implying a window full of unrecorded deliveries; the test schema was also missing `scheduled_instant` and `delivery_outcome` entirely, which is part of why the gap was invisible.
- Cron 24-hour aggregates no longer drop unresolved executions. The window SQL bucketed only `completed`, `failed`, and `running`/`claimed`, so a row with any other status — including `unknown`, which is a real hermes-agent terminal state that its own retention pruning names explicitly — contributed to none of them and disappeared from the summary while still occupying the table. A window containing only such a row rendered as a placeholder dash, indistinguishable from a job with no history. The window now counts a fourth `unknown_24h` bucket as the complement of the three recognized ones (NULL included), renders it as `1?`, and exposes a `total_24h` denominator so the buckets can be checked to reconcile. Unknown is deliberately not folded into `failed`, which would imply a retry is safe.
- Gateway platform records are no longer presented without establishing who wrote them. Upstream stamps `writer_pid`/`writer_start_time` on every platform entry while re-stamping the top-level `pid`/`start_time` on each write, and hermesd dropped both — so an entry preserved from an earlier gateway life was indistinguishable from one the running process just wrote. Ownership is now classified by exact `(pid, start_time)` equality (upstream's own live-vs-preserved rule) into `current`, `preserved`, or `unverifiable`, rendered as a new **Owner** column plus a compact `⚠ N platform record(s) outlived their writer` warning, and evaluated independently of heartbeat freshness — a ticking loop says nothing about who wrote a given row. All four identity values must be present: a record from a gateway that predates writer provenance, or one whose host could not resolve a process start time, reads as unverifiable rather than silently passing as current, and a matching PID with a different start time reads as preserved, since PID equality alone is not identity.
- A discovered plugin is no longer reported as enabled just because it is on disk. hermes-agent requires an explicit `plugins.enabled` opt-in, but hermesd inferred activation from the deny list alone (`enabled = name not in disabled`), so an ordinary user plugin with empty `enabled` and `disabled` lists rendered as available when it would never load. `PluginInfo.enabled` is now derived from an explicit `activation` state produced by a new `hermesd/collect/plugins.py` reader that mirrors upstream's `gate_manifest` order: legacy-Relay refusal (`removed`), deny list (`disabled`, which beats the allow-list), category-owned kinds (`category_owned` for `exclusive` memory providers; `model-provider` is active via providers discovery), then the `plugins.enabled` opt-in (`not_enabled` when absent). Both the path-derived manifest `key` and the bare `name` are matched against each list, so canonical and legacy spellings both resolve. A manifest that exists but does not parse is reported as `unknown` with a reason instead of being silently dropped, while a manifest-less directory is still skipped because upstream reads it as a category, not a plugin. Where `kind` is undeclared, hermesd scans the first 8 KiB of `__init__.py` for provider markers exactly as upstream does — text only, never importing or executing plugin code. The Skills panel's `Enabled` Yes/No column becomes an **Activation** column carrying these states; activation describes what the configuration says hermes-agent would do, not proof a plugin loaded.
- MCP cache membership no longer changes with the display cap. The schema-cache reader reported the true cached count but kept only the first 20 names, and the Skills panel computed "which configured servers are missing" by subtracting that truncated list — so with 21 cached servers the 21st was reported as absent purely because it fell off a presentation limit. Membership is now computed in the collector from the complete configured *and* cached name sets (`ConfigSummary.mcp_server_names` is display-bounded too, so neither side can be used for the join), the panel renders the resulting `mcp_uncached_server_count`/`mcp_uncached_server_names`, and a capped list shows `(+N more)` instead of silently looking complete.
- The Skills panel no longer claims a server "Never connected". Absence from `cache/mcp_schema_cache.json` is an observation about one read, not a connection history — the cache can be cleared, invalidated, or written under another profile — so the row is now **No cache entry**. An absent cache file is distinguished from an empty or unreadable one via `mcp_cache_present` and renders as `no cache file observed`, and a stale or unreadable cache still fails the `mcp_cache` source into health rather than being presented as current.
- Update/runtime code-skew detection now reads the same evidence upstream does. `plan.runtimes[].code_sha` is captured *before* the pull, so a finished update's plan always disagrees with the running tree: hermesd reported `⚠ code skew` on healthy fleets (false positive) while a fleet that genuinely came back on the wrong build passed silently whenever its pre-update plan happened to match (false negative). The post-restart `fleet` matrix is now authoritative — including its explicit `stale` state, which counts as skew even when that row never stamped a sha — and the pre-update plan is consulted only when there is no fleet matrix *and* the receipt shows the run never finished (non-zero exit, `failed`/`partial`/`running`/`refused` outcome, or an incomplete gateway restart). A `stop_reason` alone no longer marks a clean receipt unfinished. The verdict now names its evidence (`runtime_code_skew_source`: `fleet`, `plan`, or empty when not assessable), the recorded fleet matrix is exposed as state counts, and an unassessable receipt says so instead of implying a clean bill of health. All of it is part of the `update_receipt` last-good payload, so a failed read keeps the prior verdict rather than clearing it.
- A successful update is no longer labeled `⚠ update failed`. hermes-agent writes `outcome` as `running | success | partial | failed`, but the gateway panel compared against `"ok"` — a value upstream never produces — so every real receipt rendered as a failure and its outcome was styled as a warning. The compact warning is now driven by the same unfinished-receipt rules as skew detection, and the test fixtures were corrected to write `outcome: "success"` with a realistic pre-update plan and post-restart fleet matrix, which is what let the mismatch survive review.
- URL redaction is now scheme-agnostic and case-insensitive: uppercase schemes (`url=HTTPS://user:pw@host/x`) and non-HTTP schemes (`ftp://`, `ssh://`) have their credentials masked in `key=<url>` argv forms and in free text, not just lowercase `http(s)` URLs. The URL and secret-field scan patterns are length-bounded so long letter runs (base64 blobs, minified JS) cannot stall log redaction quadratically.
- Secret-text redaction no longer propagates `RecursionError` (or any other structured-path failure) on deeply nested JSON log lines: parse, redact, and re-serialize are guarded as one unit and fail closed to the line-oriented redactor, keeping the sanitizer-never-raises guarantee at its collector and cron call sites.
- Unquoted multi-word secret values in log text (e.g. `password=my secret pass`) no longer leak their tail: the bare-value form is redacted to the next top-level `,`, `}`, `]`, or end-of-line (failing closed on space-separated prose), while an already-redacted URL following the value stays visible.
- Argv redaction now covers `key=<url>` forms (e.g. `url=https://user:pw@host/x?token=t1` and `--url=https://…`): the URL value has its userinfo and secret query parameters masked instead of passing through byte-identical because the `key=` prefix defeated whole-argument URL detection.
- Snapshot export (`--snapshot-file`) now writes to a temporary file that is atomically renamed into place: a destination hard-linked to a file inside `~/.hermes/` can no longer truncate the protected file, and failed or interrupted writes clean up their partial temporary output.
- Secret redaction is now consistent across representations: JSON-style `"api_key": "..."` text, quoted values containing spaces, keys with whitespace around the separator, and nested dict/list arguments (e.g. `private_token`) are all redacted through one canonical secret-key classifier, and the `billing_base_url` endpoint is redacted where it enters dashboard state, breakdown labels, and JSON snapshots.
- Redaction also covers escaped or truncated quoted values, structured secret values in prefixed log messages, and malformed URLs with encoded secret keys or no path before their query string.
- Exception sanitization no longer raises on malformed URLs (e.g. invalid IPv6 literals or ports inside error messages), so a single poisoned source value can no longer abort startup or `--snapshot` runs; malformed URLs still have credentials and secret query parameters masked.
- Last-good fallback baselines are now tracked per source instead of per fully clean pass: a source that succeeds keeps advancing its own fallback even while an unrelated source is failing, so a later failure no longer regresses the display to older data.
- State-snapshot directory read failures now surface in health and retain that source's last-good counts without reverting unrelated Operations fields.
- Stale cached YAML reads (e.g. config.yaml that became malformed after a good read) now mark the affected sources degraded in health while the last-good values stay on display — matching the existing JSON behavior — instead of silently showing stale data with green health. Intentionally absent optional files remain healthy.

Deterministic failures (malformed JSON/YAML, oversize) still skip re-parsing until the file changes.

- `runtime/active_sessions.json` is capped at 200 entries so an oversized file cannot stall the collector with one liveness probe per entry.
- The opt-in live contract test applies the same hidden-session filter as the reader, so it passes on homes with hidden sessions.
- On Python 3.14, an unreadable `logs/` directory is reported as a failed source (with last-good lines kept) instead of "no logs": `Path.exists()` now returns False on permission errors there, so the logs reader uses a strict existence check that only treats absence as absence.
- Quitting no longer waits for a full collection pass: `close()` signals the in-flight pass, which stops after the current source and keeps last-good values for the rest.
- Logs and Skills detail views clamp a negative scroll offset to the top instead of slicing from the end and rendering an empty page with a `[-4--5/30]` counter.
- A `config.yaml` truncated to zero bytes (for example mid-write) now fails the config source and keeps the last-good summary instead of blanking the Config panel to defaults.
- A corrupt or undecodable session file in the legacy `sessions/` scan now fails the tools source and preserves the last-good tool inventory instead of silently shrinking it.
- Gateway no longer reports "config stale" permanently: staleness is now derived from `config.yaml`'s mtime against the running gateway's start time (`state/gateway.heartbeat`, `state/gateway.lifecycle.json`, then `gateway_state.json`, ignoring monotonic-clock values), instead of the orphan `config_generation` mtimes that no current hermes-agent writes. A symlinked `config.yaml` (dotfiles setups) is still evaluated, and no known start time reports not-stale.
- A process ID too large for the OS (for example `2**40` in `gateway_state.json`, `runtime/active_sessions.json` or `spawn-ledger.json`) no longer raises `OverflowError` and fails the whole source; it is simply reported as not alive.
- `runtime/active_sessions.json`, `desktop-build-stamp.json` and `web-ui-build-stamp.json` are now confined to `~/.hermes` like every other read, and `cron/executions.db`, `cron/ticker_heartbeat` and `cron/ticker_last_success` are confined to the Hermes home rather than only checked for being symlinks themselves — a symlinked `cron/` directory no longer escapes. An `executions.db` swapped for an outside path after a good read keeps the last-good executions and names the source failed.
- JSON/YAML files under `~/.hermes` are refused above 8 MiB instead of being parsed whole and retained forever; the 4.5 MB `models_dev_cache.json` still loads, and an over-cap file keeps the last-good value like a malformed one.
- Goal records in `state_meta` are now decoded through the same size-capped JSON helper as delegation payloads, and that cap is raised from 4 KiB to 64 KiB so realistic delegation tasks and results are no longer blanked.
- `state.db` is snapshotted once per change instead of twice per refresh: the goals/delegations/ledger readout now runs on the read-only connection `HermesDB` already holds, halving the WAL copy cost on non-APFS filesystems. A corrupt `state.db` still falls back to last-good data for those sources.
- Cron output lines are truncated to 4096 characters before redaction, matching the log reader, so a single 20 000-character line cannot slow a refresh.
- Database existence checks (`state.db`, `kanban.db`, `response_store.db`, `verification_evidence.db`, `projects.db`) use the strict existence probe, so on Python 3.14 an unreadable directory marks the source failed instead of reporting an empty database.
